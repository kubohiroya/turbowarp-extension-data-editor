# 複合エディター：固定入力とJSON入力を1つの画面で編集する（設計）

状態: 設計。中心部分（固定入力の段の種類`json`）を実装中。

## 背景

登録簿は1つのopcodeに編集画面を1つしか登録できない（`registry.ts`の重複検査）。このため、固定入力（選択肢など）とJSON入力を両方持つブロックでは、片方しか編集画面を持てない。例は`turbowarp-named-functions`の`define function`で、`EXPORT`（`none`/`tool`）は固定入力の編集画面を持つが、`SCHEMA`と`RETURNS`（JSON Schema、またはスキーマ名）は編集できない。

検討した2案のうち、「1つのopcodeに複数の編集画面を登録し、タブで選ぶ」案は採らない。タブごとの保存になり、入力をまたぐ検査（例：`tool`として公開するなら説明が必須）ができないためである。代わりに、1つのブロックの入力を1つの下書きとして編集し、1回で保存する複合エディターを、固定入力の編集画面の拡張として作る。

## 既存の部品との関係

- `registerFixedInputEditor`は、固定入力を有限のpolicyで扱う（[fixed-input-contracts.md](fixed-input-contracts.md)）。すでに次のものを備える。
  - 複数のbindingを1つの画面に並べ、1回のSaveで単一transactionとして保存する。
  - レポーターが差し込まれた入力を読み取り専用で表示する。
  - 保存できない間はSaveを押せなくする。
  - 各bindingの`validateCandidate(candidate, context, finalSnapshot)`が、保存後の全入力を受け取る。入力をまたぐ検査はここで書ける。
- JSONの入力もブロック上では文字列の値である。

そこで、複合エディターは新しい登録APIを作らず、固定入力の段の種類に`json`を足して実現する。保存経路も既存の安全対策（リビジョン照合、単一transaction）もそのまま使う。

## 登録API

```ts
interface FixedInputControl {
  kind: 'text' | 'number' | 'enum' | 'color' | 'json';
  /** jsonのみ。ベーシックのフォームに使う共通スキーマ。 */
  basic?: 'json-schema';
  // 既存の項目は略
}

interface FixedInputBinding<C = null> {
  // 既存の項目（argument, control, schemaBundle, read, encode, validateCandidate など）は略
  /** jsonのみ。「名前で指定」の一覧。ブロックの版ごとに1回だけ呼ぶ。 */
  listNames?(snapshot: FixedBlockSnapshot): readonly string[];
}
```

- `listNames`と`basic`は`json`以外の段に付けると登録時に拒否する。
- 値の扱いはownerの`read`と`encode`で決める。段の値が文字列なら名前、それ以外ならJSONデータとする。`read`は保存済みの文字列をこの値に直し（JSONとして読めなければ名前）、`encode`は名前ならそのまま、それ以外はJSONの文字列にする。
- 既存の登録APIと「1つのopcodeに編集画面は1つ」の規則は変えない。

## 画面

- 各bindingを段として縦に並べる。固定入力の段は今と同じく1行で表示する。
- JSONの段は`<details>`で開閉できる。保存できない問題があれば自動で開く。
- JSONの段の見出しに状態を表示する。保存できる状態なら☑、問題があれば⚠を付ける。任意の入力が空なのは「保存できる状態」とみなす。
- 保存ボタンは、全段が保存できる状態のときだけ押せる（ラベルと、変更がないときの扱いは「保存ボタンのラベル」の節）。
- 保存ボタンを押せなくするのは、この画面の指針（押せないボタンを避け、操作に応じて理由を示す）の例外とする。根拠は、理由を常に保存ボタンの横に表示すること、問題のある段を自動で開いてエラー文をその場に出すことで、押せない理由が画面上で分かるためである。
- 入力にレポーターが差し込まれている段は、既存の固定入力と同じく読み取り専用で表示する。保存はその入力を書き換えない。
- 押せないときにボタンの横へ出す理由は、次の優先順で1つだけ出す。
  1. 直すべき問題がある：「n件の問題を直すと保存できます」。
  2. Updateで、変更がない：「変更はありません」。
- `validateCandidate`が返す問題は、`path`が指す段に表示する。
- 判定は入力中に随時行い、状態を即座に更新する。

## JSONの段の3つのモード

| モード | 内容 |
|---|---|
| 名前で指定 | `listNames`が返す一覧から選ぶ（例：`define schema`の定義名）。`listNames`が無い段では出さない |
| ベーシック | `basic`が指す共通スキーマからRJSFでフォームを作る。`basic`が無い段では出さない |
| エキスパート | JSONをテキストエリアで直接書く |

- **ベーシック用スキーマ**：JSON SchemaのメタスキーマそのものはRJSFでは扱えない（再帰、`$dynamicRef`、真偽値スキーマ、配列の`type`）。そこで、範囲を絞った共通スキーマを使う（「ベーシック用スキーマの所在」の節）。
- **ベーシックで表せるかの判定**：`fitsBasicJsonSchema(value)`で行う。
- **最初に開くモード**：値が文字列（名前）なら「名前で指定」、ベーシックで表せればベーシック、それ以外はエキスパート。
- **ベーシック→エキスパート**：いつでも切り替えられる。
- **エキスパート→ベーシック**：JSONとして読めない文字列は保存できず、段は⚠になる。ベーシックで表せない機能を含むときは、フォームを読み取り専用で表示し、「ベーシックモードでは表せない内容が含まれています」と知らせる。フォームから保存して機能が黙って消えることを防ぐ。値が空なら「ベーシックのスキーマを始める」ボタンを出す。
- 段の☑と保存ボタンの判定はモードに依存せず、最終的な値で行う。

## 保存

- 全段の候補を一度に作り、各bindingの`validateCandidate`に通す。
- 通ったら、変更のあった入力だけを1つのtransactionとして書き込む（Undoは1回分）。
- 書き込み直前に、既存のリビジョン照合で衝突を検出する。

## 最初の利用者

`turbowarp-named-functions`の`define function`で使う。

- `EXPORT`：固定入力の段（既存のbindingをそのまま移す）
- `SCHEMA`：JSONの段。3つのモードすべてを使う
- `RETURNS`：JSONの段。空を許す
- 入力をまたぐ検査：`EXPORT`が`tool`なら`DESCRIPTION`が必須、という既存の規則（`function-registry.ts`の`readDefinition`）。`validateCandidate`の保存後スナップショットから`DESCRIPTION`を読む

## ベーシック用スキーマの所在

「JSON Schemaを書くためのスキーマ」（プロパティの一覧、型、必須、説明、`enum`、最小・最大、配列の要素の型）と、それに対応する`fits`は、data-editorの共通部品として`./schema`から提供する。JSON Schemaを入力に持つ拡張は他にもありうるため、拡張ごとに作ると二重になる。named-functionsは、`define schema`ブロックが扱う範囲がこの共通部品と一致することをテストで確かめる。共通部品は、最初の利用者の実装より前に用意する。

## 保存ボタンのラベル

- ブロックのすべての入力が、拡張の定義する初期値（パレットから置いたときの値）のままなら「Save」とする。未変更でも押せる。押すと内容を確かめてダイアログを閉じ、何も書き込まない（「保存」の節のとおり、変更のあった入力だけを書き込むため）。Undoの履歴も増えない。
- 一つでも初期値と違う入力があれば「Update」とする。下書きが保存済みの値から変わっていないときは押せず、変わると押せる。「Updateが押せない＝変更がない」と読めるようにするためである。
- 判定は、拡張の初期値と現在の値を比べるだけで行い、保存した事実は記録しない。手で初期値に戻したブロックも「Save」になるが、実害は小さい。
- 初期値はホストが渡す。ホストはブロック定義（拡張の`getInfo`の`arguments[].defaultValue`）から各入力の初期値を読み、スナップショットに含める。拡張側の登録APIは変えない。単独の編集画面に揃えるときも、同じスナップショットの値を使う。
- 押せない条件（全段が整うまで）は、どちらのラベルでも同じく適用する。

## 単独の編集画面との揃え方

- 単独の編集画面（入力が1つ、または段に分けない画面）には☑️を出さない。段が1つしかなければ、保存ボタンが押せるかどうかだけで状態が分かるためである。
- 保存ボタンのラベル（Save／Update）と押せる条件、押せないときにボタンの横へ理由を出す規則は、単独の編集画面にも揃える。同じEditorの中で保存の振る舞いを1通りにするためである。
- この揃え込みは既存の編集画面のUIを変える。複合エディターとは別の変更として段階を分け、既存のE2E（ローカル実行）を合わせて更新する。

## 既存の編集画面への影響

- 複合エディターは固定入力の段の種類を足すだけで、既存の登録APIと「1つのopcodeに編集画面は1つ」の規則は変えない。複合エディターの導入だけでは、移したブロック以外の画面の見た目も動作も変わらない。保存ボタンの揃え込み（前節）は別の段階で行う。
- JSONの段は固定入力の表示に足す。固定入力の表示そのものに手を入れる場合は、既存の単独の編集画面の表示が変わっていないことを既存のE2E（ローカル実行）で確かめる。

## 保留

- 段の開閉などUIの状態を、同じブロックを次に開いたときに覚えておく機能。必要になったら追加する。
